# 参数与时长

## 先区分三种时间

- 视频时长：观众看到的播放长度，例如 30 秒。
- 推理耗时：机器执行工作流用的墙钟时间，例如某段耗时 253.489 秒。
- 排队/加载/后期：会影响总等待时间，不能与前两者混为一谈。

## 帧数怎么算

本机节点 `temporal_shape` / `align_frame_count` 使用 24fps，并把请求帧数向上对齐到 `N = 17k + 5`，至少 5 帧。

`请求帧数 = ceil(目标秒数 × 24)`；`实际帧数 = 5 + 17 × ceil((max(5,请求帧数)-5)/17)`；`播放秒数 = 实际帧数 / 24`。

| 目标 | 请求帧数 | 实际生成帧数 | 24fps 播放时长 | 精确时长后期处理 |
|---|---:|---:|---:|---|
| 3 秒 | 72 | 73 | 3.0417 秒 | 裁成 72 帧 |
| 5 秒 | 120 | 124 | 5.1667 秒 | 裁成 120 帧 |
| 10 秒 | 240 | 243 | 10.125 秒 | 裁成 240 帧 |
| 15 秒 | 360 | 362 | 15.0833 秒 | 裁成 360 帧 |
| 30 秒 | 720 | 736 | 30.6667 秒 | 不作为已验证单次配置，优先分段 |

124–362 帧约为本机节点注释的训练时长范围；界面允许填到 3600 不代表长片质量、显存与稳定性经过验证。我们确实跑过 73 帧短片，但短于此范围的结果也不能据此推广。

不要只把输出 fps 改为 30 来“提速”：相同帧数会缩短视频、改变动作速度，且音轨可能不同步。需要保持动作速度的升帧应另做插帧和音画核验。

## 我们实际用到的参数

| 参数 | 本次配置 | 调整影响 |
|---|---|---|
| width / height | 352×608；416×736 | 两边按 32 的倍数设定；更大画幅通常消耗更多显存/时间 |
| length | 73、260、362 等 | 请求视频帧数；实际值会对齐 |
| CreateVideo.fps | 24 | 输出播放速度；与模型时间轴保持一致 |
| scheduler / sampler | simple / res_multistep | 与现有 Turbo 工作流一起复用 |
| steps | 8 | 实跑 Turbo 配置；不要脱离对应 LoRA 只改成 8 步 |
| denoise | 1.0 | 当前从空潜空间采样；不是关键帧强度滑块 |
| LoRA strength_model | 1.0 | 本次加速 LoRA 强度 |
| noise_seed | 每段固定并记录 | 固定种子便于比较，跨版本设备仍不保证逐位复现 |
| first_frame / last_frame | 可选图片连接 | 决定两端参考，不决定成片总帧数 |

`BasicGuider` 当前没有 CFG 数字输入；不要把 Qwen 图像编辑的 CFG=1 混写成 H3 参数。

## 快速计算

运行 `python tools/frame_plan.py 15` 输出目标、对齐帧数、尾帧索引与裁剪帧数。工具只计算，不提交任务、不下载模型。小数秒只有落在 1/24 秒网格时才能靠整帧完全精确表达。
